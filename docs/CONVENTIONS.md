# 代码与文档约定

## 注释

`src/` 与 `scripts/` 零解释性注释:文件头、字段说明、"为什么这么写"都不写。代码靠命名和结构说清做什么、为什么;要靠注释才读得懂,先改代码(换名、拆函数、把约束写进类型或断言)。

例外是机器要读的指令:`@ts-expect-error`、`/* @__PURE__ */`、生成文件头。保留指令本身,不附带解释。

## 决定记在哪

判据:删掉这句说明,只看代码会不会做错事。

- 外部契约与行为边界(DSH 契约、第三方 API 行为、槽位/设置/bundle 形态、注入匹配口径、配置持久化)→ README「行为与边界」(建立前暂记任务清单 §3–§4);
- 方向级、难逆转的取舍 → `docs/adr/000N-*.md`(递增编号,不改旧文;第一次出现时建目录);
- 运行与验证纪律、踩过的坑 → AGENTS.md「安全与边界」;
- 安装与排查 → README 故障排查。

同一条规则只写一处,别处引用、不复述。任务清单是本次任务书,不是长期契约:实现必须偏离它时先问我;确认后把新事实记进 README/ADR,不要悄悄偏离,也不要回头把它改写成"现状"。

新增或改动记录后,当次回复里说清:动了哪份文件、记了什么、为什么代码里放不下。

## 构建与产物

环境:DSH `0.2.2-alpha.2`、Node v24.15.0、npm 11.14.1(2026-11-02 核对;之后以 README「环境」为准)。

`npm run build` 是产物不是检查:esbuild 出 `lib/index.js`(host,node ESM)与 `lib/client.js`(browser,lazy-CJS)。`src/` 是唯一真源,`lib/` 只由构建生成、永远不手改;是否入库由我定。`npm run typecheck` 只查 `src/`。

生效方式:host 改动要重启 `dsh web` 才加载新 `lib/index.js`(插件目录不在 HMR root 面内),重启只由我做;browser 改动重建后由我刷新页面验收(旧 bundle 可能被缓存)。

## 提交

建仓、`lib/` 是否入库、怎么提交先问我;沿用参考仓库习惯时用 `feat/fix/docs/chore:` + 中文主语,`src/` 与重建的 `lib/`(若纳入)同一提交。

## 写作

像跟同事说话:熟悉的词优先,一段只说一件事;同一概念不换叫法(先按任务清单的用法,写 README 时统一定名)。
